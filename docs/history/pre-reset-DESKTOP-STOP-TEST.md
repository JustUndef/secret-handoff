# Manual Codex Desktop Stop observation

This test-only procedure uses synthetic input and does not establish general Desktop compatibility or security isolation. The October 29, 2026 human-assisted run recorded `OBSERVER_STOP_TIMEOUT`; see [TESTING.md](TESTING.md) for the result and execution-path limits. It needs the built test runner and synthetic probe. The launcher is invoked directly with its normal --watch-caller option; the observer is not a production dependency.

1. Run scripts/Build-Prototype.ps1 in a context permitting Windows metadata queries. Choose a reviewed launcher EXE with --watch-caller. Close other Secret Handoff requests.
2. The human opens a new, ordinary PowerShell terminal from the Windows Start menu, independently of the Codex task. This console must stay open; it is not a process detached from a Codex tool. From the project root, choose a fresh, nonexistent session directory and run:

       & '.\tests\SecretHandoff.Tests\bin\Debug\net10.0-windows\SecretHandoff.Tests.exe' --desktop-observer 'C:\path\to\checkout\artifacts\desktop-stop-unique-session' 'C:\path\to\reviewed\SecretHandoff.exe'

   The observer creates the directory and setup.json; it waits at most five minutes for the test tree. The paths in this example are metadata, not secret values. Do not reuse a directory. The session records only fixed categories and process IDs and creation times, never secret values or process output.
3. The agent reads setup.json and invokes the exact launcherPath through its ordinary waiting process tool, passing separate arguments: --watch-caller --secret EXAMPLE_API_TOKEN --working-directory <project root> -- <probe> tree <marker> wait. Use the probe and marker from setup.json. The probe is the built synthetic test executable and remains running with one synthetic child. Do not wrap the launcher in a new runtime script, use a request file, or interrupt the tool yet.
4. The human enters a synthetic value such as synthetic-demo-one in the local masked dialog and explicitly approves the fully displayed invocation. The agent must not fill or approve this manual dialog.
5. Wait for OBSERVER_READY_PRESS_ENTER_TO_ARM in the separate terminal and for ready.json. The observer has pinned live handles, checked exact executable paths, parent relationships and creation times, and verified that the launcher was created after the observer. If it fails or times out before readiness, use the local Cancel action if the launcher is still open; no Stop conclusion is possible.
6. The human presses Enter in the observer terminal. Only after OBSERVER_ARMED_PRESS_DESKTOP_STOP_NOW and armed.txt appear, immediately press the actual Codex Desktop Stop control for the waiting launcher tool. The armed observation window is 30 seconds; all four handles must be live at arming. Do not substitute Ctrl+C or local Cancel.
7. Read result.txt and, when present, observed.json in the session directory. OBSERVER_ALL_ENDED_AFTER_ARM means the retained launcher, target, and child handles became signalled within the armed window and subsequent ten-second cleanup observation. observed.json records the caller separately: a caller may remain alive if the host directly terminates the launcher. The human must confirm that Desktop Stop was actually pressed in the armed interval; the observer cannot detect the button press itself. Any other result is not a pass. The observer writes its result before any failure cleanup and then attempts to stop only the verified launcher/target/child via retained handles. It never kills the caller. If identity was not fully verified, it does not kill anything; use local Cancel if needed.

The observer itself exits after a bounded setup, arming and observation period. OBSERVER_STOP_TIMEOUT means no observed process ended in the 30-second armed window; it is recorded before cleanup. Other fixed failure categories distinguish setup, identity, premature exit and incomplete termination. ready.json contains retained process IDs and Windows creation FILETIMEs for reproducibility; observed.json records whether each retained handle was still live before observer cleanup. Process names, PIDs alone, and an observer launched inside the interrupted task are insufficient evidence.
